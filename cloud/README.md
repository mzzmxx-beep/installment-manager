# البنية السحابية (Cloud / SaaS)

كود ومخططات المرحلة الجديدة من المشروع — منتج ويب (PWA) متعدد المستأجرين على
Cloudflare، بديلاً كاملاً عن تطبيق الويندوز الأوفلاين. التفاصيل والمراحل
الكاملة موثقة بـ [خطة-التحول-السحابي.md](../خطة-التحول-السحابي.md).

## الهيكل

- `control-plane/` — قاعدة D1 المشتركة الوحيدة: سجل الزبائن (tenants)،
  الحسابات (accounts)، وحالة الاشتراك. لا تحتوي أي بيانات تجارية.
- `tenant-template/` — مخطط D1 يُطبَّق على قاعدة بيانات منفصلة لكل زبون
  (محل) عند إنشائه. نفس مخطط SQLite الأصلي من التطبيق الأوفلاين، محوّل
  لمعرّفات UUID، وبدون جدول الترخيص (`license_activation` أصبح بلا معنى —
  حالة الاشتراك تُتحقق مركزياً من الآن فصاعداً)، وبدون مستمسكات الزبون
  (`customer_document`) — أُلغيت من نطاق المنتج السحابي بقرار.

## حالة المرحلة 1 (تم التحقق يدوياً)

تم إنشاء وربط قاعدتي بيانات حقيقيتين على Cloudflare للتحقق من صحة الفكرة:

| القاعدة | الاسم على Cloudflare | الغرض |
|---|---|---|
| Control Plane | `installment-control-plane` | سجل الزبائن والحسابات |
| زبون تجريبي | `tenant-demo-shop` | بيانات تجارية معزولة لزبون واحد تجريبي |

تم التحقق يدوياً عبر `wrangler d1 execute` من: إنشاء زبون تجريبي بالـ Control
Plane، إنشاء حساب مالك مرتبط به، ثم إدخال زبون وفاتورة بيع فعلية بقاعدة
الزبون التجريبي المنفصلة — وقراءتها بنجاح، ما يثبت أن العزل بين القاعدتين
والربط بينهما (عبر `d1_database_id`) يعمل كما هو مخطط.

معرّفات القواعد الفعلية (غير سرية — مجرد أسماء موارد Cloudflare) موجودة عبر
`wrangler d1 list`.

## حالة المرحلة 2 (Worker منشور وشغّال فعلياً)

الكود بمجلد `api/` — منشور فعلياً على:

```
https://installment-api.mzzmxx.workers.dev
```

**تم بناؤه واختباره فعلياً (نهاية-لنهاية، على القاعدتين الحقيقيتين):**

- `POST /auth/login` — تسجيل دخول، يرجع جلسة (JWT) صالحة أسبوع.
- طبقة وسيطة (middleware) على كل مسار `/api/*`: تتحقق من الجلسة، **وتعيد
  التحقق من حالة الاشتراك بكل طلب** (مو بس عند تسجيل الدخول) — جرّبتها
  فعلياً بتعليق اشتراك الزبون التجريبي مؤقتاً والتأكد إن كل الطلبات تُرفض
  فوراً (403) حتى مع جلسة صالحة، ثم رجعته لحالته.
- `POST/GET /api/customers`, `POST/GET /api/products` — نفس منطق
  `repo/customer.rs` و`repo/product.rs` الأصلي.
- `POST /api/sales`, `GET /api/customers/:id/sales` — نفس منطق
  `repo/sale.rs::create_credit_sale` بالضبط: تحويل عملة كل صنف، احتساب
  الهامش، توليد جدول الأقساط، بمعاملة ذرية واحدة (`D1.batch`، مكافئ
  `tx.commit()`).
- `POST /api/payments`, `GET /api/customers/:id/payments` — نفس منطق
  `repo/payment.rs::register_payment` بالضبط: توزيع الدفعة الأقدم-أولاً
  عبر العملات، تحديث حالة كل قسط، تسجيل بسجل التتبع (audit_log).
- `engine.ts` — نسخة طبق الأصل من `engine.rs` (نفس قواعد التقريب، توزيع
  الأقساط، تحويل العملة) — تحققت يدوياً من نتائجها ضد نفس الأمثلة
  الموجودة باختبارات Rust الأصلية (مثال: بيع ٣٣٠,٠٠٠ دينار / ٣ أقساط،
  دفعة ١٥٠,٠٠٠ توزّعت ١١٠,٠٠٠ + ٤٠,٠٠٠ بالضبط كما متوقع).

**التقارير والتحليلات — انتقلت بالكامل واختُبرت فعلياً:**

- `GET /api/customers/:id/statement` — كشف الزبون الكامل (فواتير + دفعات
  + الرصيد المتبقي بكل عملة).
- `GET /api/reports/overdue-installments` — كل الأقساط المتأخرة.
- `GET /api/reports/sales-summary` — إجمالي المبيعات والربح والمُحصَّل/
  المتبقي بكل عملة.
- `GET /api/reports/top-products`, `/top-customers`,
  `/most-overdue-customers`, `/customers-overview` — التصنيفات والملخصات.
- `GET /api/reports/sale-conversions`, `/payment-conversions`,
  `/product-conversion-summary`, `/customer-conversion-summary` — تقارير
  تحويل العملة (بما فيها إعادة اشتقاق السعر الأصلي قبل التحويل، أعقد جزء
  بهذه المجموعة) — اختُبرت يدوياً ببيع منتج مسعّر بالدولار ضمن فاتورة
  بالدينار وتأكدت الأرقام مطابقة تماماً لمنطق `currency_report.rs` الأصلي.

**بهذا اكتملت المرحلة 2** — كل وظائف التطبيق الأصلي منقولة (مستمسكات
الزبون أُلغيت من النطاق بقرار، وليست فجوة تقنية). المتبقي فقط:

- حساب/تسجيل زبون جديد تلقائي من التطبيق نفسه — حالياً حساب الزبون
  التجريبي أُنشئ يدوياً عبر `wrangler d1 execute` (هذا أصلاً موضوع
  المرحلة 4: التزويد التلقائي من لوحة التحكم).

## قرار/قيد تقني مهم اكتشفناه أثناء التنفيذ

الـ Worker حالياً معرّف بربط ثابت (`binding`) بقاعدة الزبون التجريبي
الوحيدة فقط (`TENANT_DEMO_DB` بـ `wrangler.toml`) — **مو ديناميكي**. هذا
يكفي لإثبات صحة كل منطق العمل (المرحلة 2)، لكنه **لا يصلح لعشرات/مئات
الزبائن** كل واحد بقاعدته الخاصة. الوصول الديناميكي لقاعدة أي زبون (حسب
هويته بجلسة الدخول) يحتاج استخدام Cloudflare D1 HTTP API بدل الربط
الثابت، وهذا يتطلب توليد Cloudflare API Token مخصص (خطوة تُسوى من لوحة
تحكم Cloudflare، مو شي أقدر أوتوماتيكياً أسويه من هنا). **هذا لازم يُحل
قبل المرحلة 4** (التزويد التلقائي لزبون جديد).

## قرار مفتوح

هذا المجلد حالياً داخل نفس مستودع تطبيق الويندوز (`installment-manager/`)
رغم قرار إلغائه بالكامل — للإبقاء على كل السياق بمكان واحد أثناء الانتقال.
ممكن نفصله لمستودع مستقل لاحقاً إذا صار مصدر تشويش.
