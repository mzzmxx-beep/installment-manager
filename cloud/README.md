# البنية السحابية (Cloud / SaaS)

كود ومخططات المرحلة الجديدة من المشروع — منتج ويب (PWA) متعدد المستأجرين على
Cloudflare، بديلاً كاملاً عن تطبيق الويندوز الأوفلاين. التفاصيل والمراحل
الكاملة موثقة بـ [خطة-التحول-السحابي.md](../خطة-التحول-السحابي.md).

## الهيكل

- `control-plane/` — قاعدة D1 المشتركة الوحيدة: سجل الزبائن (tenants)،
  الحسابات (accounts)، وحالة الاشتراك. لا تحتوي أي بيانات تجارية.
- `tenant-template/` — مخطط D1 يُطبَّق على قاعدة بيانات منفصلة لكل زبون
  (محل) عند إنشائه. نفس مخطط SQLite الأصلي من التطبيق الأوفلاين، محوّل
  لمعرّفات UUID، وبدون جدول الترخيص (`license_activation` أصبح بلا معنى —
  حالة الاشتراك تُتحقق مركزياً من الآن فصاعداً)، وبدون مستمسكات الزبون
  (`customer_document`) — أُلغيت من نطاق المنتج السحابي بقرار.

## حالة المرحلة 1 (تم التحقق يدوياً)

تم إنشاء وربط قاعدتي بيانات حقيقيتين على Cloudflare للتحقق من صحة الفكرة:

| القاعدة | الاسم على Cloudflare | الغرض |
|---|---|---|
| Control Plane | `installment-control-plane` | سجل الزبائن والحسابات |
| زبون تجريبي | `tenant-demo-shop` | بيانات تجارية معزولة لزبون واحد تجريبي |

تم التحقق يدوياً عبر `wrangler d1 execute` من: إنشاء زبون تجريبي بالـ Control
Plane، إنشاء حساب مالك مرتبط به، ثم إدخال زبون وفاتورة بيع فعلية بقاعدة
الزبون التجريبي المنفصلة — وقراءتها بنجاح، ما يثبت أن العزل بين القاعدتين
والربط بينهما (عبر `d1_database_id`) يعمل كما هو مخطط.

معرّفات القواعد الفعلية (غير سرية — مجرد أسماء موارد Cloudflare) موجودة عبر
`wrangler d1 list`.

## حالة المرحلة 2 (Worker منشور وشغّال فعلياً)

الكود بمجلد `api/` — منشور فعلياً على:

```
https://installment-api.mzzmxx.workers.dev
```

**تم بناؤه واختباره فعلياً (نهاية-لنهاية، على القاعدتين الحقيقيتين):**

- `POST /auth/login` — تسجيل دخول، يرجع جلسة (JWT) صالحة أسبوع.
- طبقة وسيطة (middleware) على كل مسار `/api/*`: تتحقق من الجلسة، **وتعيد
  التحقق من حالة الاشتراك بكل طلب** (مو بس عند تسجيل الدخول) — جرّبتها
  فعلياً بتعليق اشتراك الزبون التجريبي مؤقتاً والتأكد إن كل الطلبات تُرفض
  فوراً (403) حتى مع جلسة صالحة، ثم رجعته لحالته.
- `POST/GET /api/customers`, `POST/GET /api/products` — نفس منطق
  `repo/customer.rs` و`repo/product.rs` الأصلي.
- `POST /api/sales`, `GET /api/customers/:id/sales` — نفس منطق
  `repo/sale.rs::create_credit_sale` بالضبط: تحويل عملة كل صنف، احتساب
  الهامش، توليد جدول الأقساط، بمعاملة ذرية واحدة (`D1.batch`، مكافئ
  `tx.commit()`).
- `POST /api/payments`, `GET /api/customers/:id/payments` — نفس منطق
  `repo/payment.rs::register_payment` بالضبط: توزيع الدفعة الأقدم-أولاً
  عبر العملات، تحديث حالة كل قسط، تسجيل بسجل التتبع (audit_log).
- `engine.ts` — نسخة طبق الأصل من `engine.rs` (نفس قواعد التقريب، توزيع
  الأقساط، تحويل العملة) — تحققت يدوياً من نتائجها ضد نفس الأمثلة
  الموجودة باختبارات Rust الأصلية (مثال: بيع ٣٣٠,٠٠٠ دينار / ٣ أقساط،
  دفعة ١٥٠,٠٠٠ توزّعت ١١٠,٠٠٠ + ٤٠,٠٠٠ بالضبط كما متوقع).

**التقارير والتحليلات — انتقلت بالكامل واختُبرت فعلياً:**

- `GET /api/customers/:id/statement` — كشف الزبون الكامل (فواتير + دفعات
  + الرصيد المتبقي بكل عملة).
- `GET /api/reports/overdue-installments` — كل الأقساط المتأخرة.
- `GET /api/reports/sales-summary` — إجمالي المبيعات والربح والمُحصَّل/
  المتبقي بكل عملة.
- `GET /api/reports/top-products`, `/top-customers`,
  `/most-overdue-customers`, `/customers-overview` — التصنيفات والملخصات.
- `GET /api/reports/sale-conversions`, `/payment-conversions`,
  `/product-conversion-summary`, `/customer-conversion-summary` — تقارير
  تحويل العملة (بما فيها إعادة اشتقاق السعر الأصلي قبل التحويل، أعقد جزء
  بهذه المجموعة) — اختُبرت يدوياً ببيع منتج مسعّر بالدولار ضمن فاتورة
  بالدينار وتأكدت الأرقام مطابقة تماماً لمنطق `currency_report.rs` الأصلي.

**بهذا اكتملت المرحلة 2** — كل وظائف التطبيق الأصلي منقولة (مستمسكات
الزبون أُلغيت من النطاق بقرار، وليست فجوة تقنية). المتبقي فقط:

- حساب/تسجيل زبون جديد تلقائي من التطبيق نفسه — حالياً حساب الزبون
  التجريبي أُنشئ يدوياً عبر `wrangler d1 execute` (هذا أصلاً موضوع
  المرحلة 4: التزويد التلقائي من لوحة التحكم).

## قرار/قيد تقني مهم اكتشفناه أثناء التنفيذ

الـ Worker حالياً معرّف بربط ثابت (`binding`) بقاعدة الزبون التجريبي
الوحيدة فقط (`TENANT_DEMO_DB` بـ `wrangler.toml`) — **مو ديناميكي**. هذا
يكفي لإثبات صحة كل منطق العمل (المرحلة 2)، لكنه **لا يصلح لعشرات/مئات
الزبائن** كل واحد بقاعدته الخاصة. الوصول الديناميكي لقاعدة أي زبون (حسب
هويته بجلسة الدخول) يحتاج استخدام Cloudflare D1 HTTP API بدل الربط
الثابت، وهذا يتطلب توليد Cloudflare API Token مخصص (خطوة تُسوى من لوحة
تحكم Cloudflare، مو شي أقدر أوتوماتيكياً أسويه من هنا). **هذا لازم يُحل
قبل المرحلة 4** (التزويد التلقائي لزبون جديد).

## حالة المرحلة 3 (PWA منشورة وشغّالة فعلياً)

الكود بمجلد `web/` — نفس واجهة React الأصلية من التطبيق الأوفلاين
(installment-manager/src)، معدَّلة لتصير PWA تتصل بالـ Worker بدل
Tauri. منشورة فعلياً على:

```
https://installment-web.pages.dev
```

**التعديلات الفعلية على الواجهة الأصلية:**

- `lib/api.ts`: كل نداءات `invoke()` صارت `fetch()` بمفتاح جلسة (JWT)،
  ومعرّفات كل شي (زبون/فاتورة/منتج) صارت نصوص UUID بدل أرقام.
- إضافة `features/auth/AuthGate.tsx` (شاشة تسجيل دخول) بدل
  `LicenseGate` — الاشتراك يُتحقق منه بالسيرفر الآن، مو بجهاز محلي.
- حُذفت الميزات غير المنطبقة على منتج ويب: `LicenseGate`،
  `UpdateChecker` (لا يوجد مثبّت ليُحدَّث)، `BackupButton` (لا توجد
  قاعدة SQLite محلية لنسخها)، `CustomerDocuments` (أُلغيت من النطاق
  بقرار سابق).
- إضافة ملف PWA manifest (قابل للتثبيت كأيقونة على الجوال والحاسوب) +
  service worker لتسريع التحميل (لا يخزّن بيانات العمل نفسها أوفلاين
  عمداً — بيانات مالية حساسة يجب أن تكون حية دائماً).
- تعديلات تنسيقية بسيطة فقط (تخطيط الشريط العلوي يصير قابل للف
  والتمرير الأفقي بدل التكسّر على الشاشات الصغيرة) — لا تغيير بشكل أو
  نوع البيانات، فقط مواقع/تنسيق كما طُلب.

**قيد تقني وُجد وحُلّ أثناء الاختبار:** الـ Worker ما كان يرسل ترويسات
CORS، فرفضت المتصفحات (لا `curl`) كل الطلبات من الواجهة. أُضيفت طبقة
CORS بأصل مفتوح (`*`) مؤقتاً — آمن هنا لأن المصادقة تعتمد على توكن
(Bearer) يرسله الكود صراحة، مو كوكيز يرسلها المتصفح تلقائياً، فما فيه
خطر CSRF. **يُفضَّل تضييقه لدومين الصفحة فقط قبل أي إطلاق تجاري حقيقي.**

**تم اختباره فعلياً (نهاية-لنهاية، على الرابط المنشور مباشرة):** تسجيل
الدخول، عرض/إضافة الزبائن والمنتجات، عرض تفاصيل الفاتورة والأقساط،
التقارير وتقرير تحويل العملة — كلها ضد بيانات حقيقية بقاعدة الزبون
التجريبي، وتطابق تماماً نفس الأرقام التي تحققنا منها بالمرحلة 2.

**لم يُبنَ بعد:** تدفق "إنشاء حساب جديد" (التسجيل الذاتي) — حالياً
الحساب التجريبي الوحيد أُنشئ يدوياً بالمرحلة 1؛ هذا أصلاً موضوع
المرحلة 4 (التزويد التلقائي من لوحة التحكم).

## حالة المرحلة 4 (لوحة التحكم منشورة، التزويد التلقائي جاهز وينتظر توكن واحد)

الكود بمجلد `admin/` — Worker مستقل بلوحة تحكم HTML بسيطة يخدمها هو نفسه
(بلا حاجة لمشروع Pages منفصل — أداة داخلية لمشغّل واحد لا تستاهل بنية
تحتية إضافية). منشور على:

```
https://installment-admin-api.mzzmxx.workers.dev
```

الدخول: `mzzmxx@gmail.com` — كلمة المرور أُرسلت لك بالمحادثة عند إنشائها
(مخزّنة كـ Worker secret، غير موجودة بأي مكان بالكود).

**تم بناؤه واختباره فعلياً من الواجهة نفسها (مو بس API):**

- تسجيل دخول الإدارة (منفصل تماماً عن حسابات الزبائن — بيانات اعتماد
  Worker secrets، بلا جدول حسابات).
- عرض كل الزبائن مع حالة الاشتراك وتاريخ الانتهاء.
- **تمديد الاشتراك 30 يوم** و**إيقافه** — بضغطة زر، مع تسجيل كل إجراء
  بجدول `subscription_event` (من فعله ومتى ولأي زبون).
- نموذج "إضافة زبون جديد" الكامل — جاهز بالواجهة والـ Backend، لكنه
  يعرض رسالة خطأ واضحة بدل الفشل الصامت لأن قطعة واحدة ناقصة (التالي).

**تم — التزويد التلقائي شغّال فعلياً.** أنشأت توكن Cloudflare API
(بصلاحية Account → D1 → Edit)، ثبّته بالـ Worker، واختبرت تدفق "إضافة
زبون جديد" الكامل من الواجهة نفسها: إنشاء قاعدة D1 جديدة (`tenant-shop-
5576f7f6`)، تطبيق كل الجداول التسعة عليها، إنشاء حساب المالك، وتسجيله
بالسجل المركزي — كله بضغطة زر واحدة، تحقّقت منه مباشرة عبر استعلام
القاعدة الجديدة (كل الجداول موجودة بالضبط).

عثرة بالطريق تستاهل التوثيق: أول توكن أعطانيه كان مقيّد بعنوان IP
افتراضياً بلوحة Cloudflare — اشتغل مع اختباراتي بسطر الأوامر (نفس شبكتك)
لكن انرفض من سيرفر Cloudflare نفسه (Worker، شبكة IP مختلفة تماماً).
انحل بإنشاء توكن ثاني بدون أي قيد IP.

## اكتشاف معماري مهم أثناء اختبار المرحلة 4 (لسه يحتاج حل)

بعد نجاح إنشاء الزبون التجريبي الآلي، اختبرت تسجيل دخوله على تطبيق
الزبائن (`installment-web`) — **ودخل بنجاح، لكن شاف بيانات الزبون
التجريبي الأصلي (أحمد جبار...) مو بياناته الفارغة الخاصة به.** هذا لأن
`installment-api` (تطبيق الزبائن) لسه مربوط برباط ثابت بقاعدة الزبون
التجريبي الوحيدة فقط (نفس القيد الموثّق بالمرحلة 2) — أي زبون جديد
يسجّل دخول يشوف بيانات الزبون التجريبي، مو بياناته. **هذا خرق فعلي
لعزل البيانات بين الزبائن، ولازم يُصلح قبل أي إطلاق حقيقي.**

حاولت حل هذا بربط ديناميكي عبر Cloudflare D1 HTTP API (نفس أسلوب
التزويد)، لكن اختبرت وتأكدت إن **D1 HTTP API لا يدعم معاملات (transactions)
متعددة العبارات إطلاقاً** — رفض صراحة أي `BEGIN`/`COMMIT` بـ SQL، ورفض
أكثر من عبارة واحدة بنفس الطلب مع معاملات. يعني ما أقدر أضمن الذرية
(atomicity) اللي تحتاجها عمليات مثل إنشاء فاتورة بيع (سطر + أقساط
متعددة يجب تنجح أو تفشل كلها سوا) عبر هذا المسار — وهذا شرط أساسي
موثّق بمعمارية المشروع الأصلية (لا يجوز ملاحظة فاتورة نصف-مكتوبة).

**الحل الصحيح:** كل زبون يحتاج ربط Worker حقيقي (binding) لقاعدته، مو
وصول HTTP ديناميكي — لأن الذرية الحقيقية بـ D1 متوفرة فقط عبر الـ
binding API (`.batch()`)، مو الـ HTTP management API. هذا يعني عند إضافة
كل زبون جديد، لازم `installment-api` نفسه يُعاد نشره وياه ربط إضافي
لقاعدة هذا الزبون. جربت هذا وتأكدت إنه يحتاج **صلاحية توكن إضافية**
(Workers Scripts Edit، غير الموجودة حالياً — التوكن الحالي عنده D1
فقط)، فهذا يحتاج جولة عمل منفصلة (وربما توكن ثاني بصلاحيات أوسع).

**بالمختصر:** إنشاء الزبون (Provisioning) يشتغل ١٠٠٪، لكن تشغيله الفعلي
بتطبيق الزبائن (Serving) لسه يحتاج هذا الحل — بيانات الزبون التجريبي
الآلي (`auto-test@example.com`) بقيت بقاعدة D1 منفصلة صحيحة، بس ما
توصلها من التطبيق حالياً.

## قرار مفتوح

هذا المجلد حالياً داخل نفس مستودع تطبيق الويندوز (`installment-manager/`)
رغم قرار إلغائه بالكامل — للإبقاء على كل السياق بمكان واحد أثناء الانتقال.
ممكن نفصله لمستودع مستقل لاحقاً إذا صار مصدر تشويش.
